# Gemini consumer retirement and successor proposal

Date: 2026-10-06. Scope: M8-T01d, following the owner's confirmation that the signed-in Google account is personal. This supersedes the unresolved account-type diagnosis in [the earlier preflight evidence](2026-10-06-gemini-preflight.md), without changing its original observations or verification results.

## Finding

Google's [consumer deprecation notice](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals), updated 2026-09-02, states that Gemini CLI stopped serving the individual/free, Google AI Pro and Google AI Ultra tiers on 2026-06-18. The [Code Assist release notes](https://docs.cloud.google.com/gemini/docs/codeassist/release-notes) and [2026-05-19 transition announcement](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) corroborate this. Existing Code Assist Standard/Enterprise access is separately supported. Google AI Pro/Ultra consumer subscriptions are not equivalent to those licenses.

The [general Gemini CLI authentication guide](https://geminicli.com/docs/get-started/authentication/) still recommends personal Google login. That is conflicting documentation; the explicit dated consumer retirement notice governs this investigation. The earlier successful OAuth flow proved credential persistence only. Its no-free-tier account response is consistent with the retirement, but is not an account-specific explanation of Google's internal eligibility decision. Retrying the same setup or creating a Cloud project cannot be represented as a supported personal-account repair. The isolated launcher already excludes inherited Google Cloud project/API-key environment variables.

No new authenticated request, OAuth flow, inference, project creation, service activation, paid subscription or billing change was made during this follow-up. The proposed eligibility-reason probe was unnecessary once the applicable service retirement was established; raw provider diagnostics were not collected.

## Concrete proposal awaiting owner direction

Investigate **Antigravity CLI as the replacement Google subscription runtime**, then enable it only after the existing M8 security, model, usage and live-evidence gates pass. Google's [migration guide](https://antigravity.google/docs/cli/gcli-migration) recommends this successor, but describes automatic profile/extension migration and shared global context. Its [Windows installation/authentication documentation](https://antigravity.google/docs/cli/install/) describes native keyring sign-in. Its [headless interface](https://antigravity.google/docs/cli/headless/) supports structured and streaming output. These are documentation findings, not measured integration compatibility.

The proposed first slice would inspect a pinned official Windows binary in an isolated qualification directory, without changing PATH or migrating existing profiles. Verify isolated configuration, native-only credentials, actual tool declarations/default-deny execution, selected Gemini model routing and included-usage/credit stops before sign-in or inference. Preserve original provider/model provenance; never relabel historical Gemini CLI results as Antigravity. Do not activate API billing, purchase a plan or transfer existing credentials. Keep production disabled if any gate cannot be enforced.

No new package, runtime or dependency has been installed. Redistribution/license terms, packaging notices, process lifecycle and the hosted agent harness's data handling need review; no assumption of Apache-2.0 or feature/security parity carries over from Gemini CLI. Alternatives are retaining the blocked Gemini CLI integration until an existing supported Code Assist entitlement is available, or an explicit later product-scope decision. The API-key route changes the project's subscription-only billing model and is not a fallback.

Approval is needed before changing the runtime target because AGENTS requires an established decision or owner approval for scope/security changes, and SPEC/PLAN currently require the three subscription integrations. This proposal neither changes those requirements nor removes Claude's owner pause. Independent M9 archive work can continue while direction is pending.
